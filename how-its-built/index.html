How Talus is built

Talus is developed with AI as the implementer, directed by a team with over 30 years of GIS experience. We disclose that up front and keep disclosing it, because the safeguard is the process, not a secret. This page describes the process.

The short version

Every substantive capability in Talus starts as a written design decision. The decision surfaces the forks, the team's domain experts resolve them, and only then is code written. The code is reviewed by a human before it is committed. Every new data path ships with a negative test that proves it denies what it should deny. Every slice gets a security review. That is the whole method, and the rest of this page is detail.

What “AI slop” actually is

The complaint open-source maintainers make about AI-generated contributions is rarely about syntax. The code is often fine. What is missing is ownership: no human understands or stands behind the decisions in it, conventions are ignored, and the review burden lands on someone else. The sharpest version of the diagnosis is that the code is well written and the decisions behind it are lacking.

Talus is built to be the structural inverse of that. The judgment is front-loaded, written down, and approved by the people accountable for it before any code exists.

The process:

  1. Decision before code. Each capability produces a design document that lays out the open questions as explicit forks. The team's domain experts resolve them before implementation begins. The decisions are the approved artifact upstream of the code, not something inferred from it afterwards.
  2. Domain experts decide; the AI implements. Architecture and product calls come from more than thirty years of GIS practice in and around local government. The AI is the implementer, not the architect.
  3. Human review and gated commits. Every commit is reviewed and approved by a person who understands it before it is made. Commits, database migrations, and destructive operations sit behind explicit approval gates the agent cannot cross on its own.
  4. Small, single-concern slices. Work is checkpointed in pieces small enough that the reasoning, not just the diff, can actually be reviewed.
  5. Enforced conventions. A written set of architecture invariants, a drift check against the product's positioning at every design decision, and a standing rule that new code reads like the code around it.
  6. The why is written down. Non-obvious choices carry their rationale: fail-closed reasoning, guard ordering, why a door is authenticated-only. This is the bar maintainers say AI contributions miss most.
  7. Verify, don't assert. Outcomes are reproduced and tested, not assumed. The deny-by-default behaviour is proven by a test suite you can run yourself.

Evidence over assertion

The proof is not “trust us.” It is the running system and what ships with it:

  • The source, under the AGPL, at github.com/TalusGIS/talus. Read the installer script and the compose file before you run them; nothing is fetched but the container images the compose file names.
  • The invariant suite in scripts/verify-invariants: negative tests that prove anonymous, wrong-user, and forged-identity requests are denied on your own install.
  • The security overview in docs/security-overview.md, including the outbound connections a deployment can make, listed one by one, and the certifications it does not yet hold. Security issues go to security@talusgis.com, a mailbox read by a person only.
  • Supply-chain hygiene: CI scanners that fail on high and critical findings that have a fix, a CycloneDX software bill of materials with every release, container images pinned by content digest, CI actions pinned by commit hash.
  • No untrusted-contributor path. Talus is maintained in-house by design. Outside pull requests are declined automatically, so the most common real-world open-source compromise, a hijacked contributor, has no ingress.

Judge the result by the working system: fail-closed, audited, and testable on your own hardware, rather than by how it was typed.

Where AI shows up in the product itself. Talus Community contains no AI at all: the code is not in the public build, and there is no token, route, or provider key in a Community install. Talus+ carries the AI assists as an optional module. Every AI answer carries a provenance footer naming the model and prompt version, the assistant explains and suggests but never runs anything, and an air-gapped Talus+ keeps every non-AI module.
